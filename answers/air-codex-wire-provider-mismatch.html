Why does the Codex agent in Air break when Codex is wired through the central CLI tool (262.1105+)?

Run ANS-6, issue AIR-7557. Researched on 2026-11-23 against the public openai/codex repository.

Short answer. In master, Air now bundles Codex rust-v0.166.0. That release added a check, in upstream PR #57840 (commit 7ce5fa7). Before every prompt, the check compares the chat's provider with the default provider in the user's Codex config. The wire tool sets that default to wire, while Air starts its chats on its own provider: custom-gateway for the JB subscription, or the provider for a personal account. The two never match, so the app-server rejects every prompt without sending anything.

Upstream already relaxed the check. PR #59503 removes it. Codex 0.168.0 (2026-11-13) was the first release to include that change, and all later releases have it. The simplest fix for Air is to bundle Codex 0.168.0 or later instead of 0.166.0. Do not stop at 0.167.0, which still has the check.

1. What happens

  • Codex is "wired" with the central CLI tool, so the user's Codex config selects model_provider = "wire" by default.
  • Air starts its own Codex app-server and opens a chat (a thread) with a provider override for the account in use. For the JB subscription that is custom-gateway.
  • On the first prompt (turn/start), Codex 0.166.0 reloads the "latest" config: user/project config, profile, and app-server launch overrides, but not the thread's own override. That config says wire. The thread says custom-gateway. The request is rejected.
  • This happens with both the JB and the personal subscription, because neither is the wire provider.
  • Users who have not wired Codex have no top-level model_provider, or one that already matches. They do not see the problem, which is why it is not reported more widely.

The error comes from the new ModelProviderError::ModelProviderMismatch variant. In 0.166.0 its text is:

This chat uses {model_provider}, but your current provider is {current_model_provider}. Switch to {model_provider} to continue.

In the reported setup, that becomes:

This chat uses custom-gateway, but your current provider is wire. Switch to custom-gateway to continue.

The JSON-RPC error carries structured data with this shape (generated TypeScript type from the PR):

export type ModelProviderError =
  | { "type": "modelProviderMismatch", modelProvider: string, currentModelProvider: string }
  | { "type": "modelProviderNotConfigured", modelProvider: string }
  | { "type": "modelProviderPolicyConflict", modelProvider: string, requiredModelProvider: string };

2. The code that causes it (Codex 0.166.0)

PR #57840 added this method to codex-rs/app-server/src/config_manager.rs. It replaced the earlier policy-only check_thread_model_provider call in turn start/steer, review, compaction and thread resume:

/// Admits resumed threads and input only on the currently selected provider.
pub(crate) async fn check_thread_model_provider_for_input(
    &self,
    current: &Config,
) -> std::io::Result<()> {
    self.check_thread_model_provider(current).await?;
    let configured = self
        .load_latest_config(Some(current.cwd.to_path_buf()))   // user config + profile + launch -c overrides
        .await?;
    if current.model_provider_id != configured.model_provider_id {   // "custom-gateway" != "wire"
        return Err(std::io::Error::new(
            std::io::ErrorKind::InvalidInput,
            ModelProviderError::ModelProviderMismatch {
                model_provider: current.model_provider_id.clone(),
                current_model_provider: configured.model_provider_id,
            },
        ));
    }
    Ok(())
}

load_latest_config builds the config from the app-server's current_cli_overrides() plus the config files. Overrides passed in thread/start are not part of it. That is the asymmetry that bites Air. thread/resume got a matching check in load_for_resume.

3. Upstream relaxed it a week later

PR #59503, "Keep threads on their saved model provider when defaults change" (commit e115d5f9, merged 2026-11-04) says:

Changing the default model provider should not prevent users from resuming or continuing a thread that uses another configured provider.

It deletes check_thread_model_provider_for_input and goes back to check_thread_model_provider. That function only compares the thread with managed provider requirements (organization policy), never with the user's default provider:

-            .check_thread_model_provider_for_input(thread.config().await.as_ref())
+            .check_thread_model_provider(thread.config().await.as_ref())

Cold resume now uses the thread's saved provider. One rule remains: a resume request that explicitly asks for a different provider than the saved one is rejected with Cannot change this thread's model provider from `X` to `Y` on resume.

4. What to do

OptionWhatPros / cons
A (recommended) Bump the Codex version bundled in Air (the revision that moved to 0.166.0) to 0.168.0 or later, e.g. 0.171.0. Removes the cause upstream intended to remove, and keeps the security fixes from newer releases. Needs a check that the newer app-server protocol still matches Air's client. Air must also not pass a different model_provider when resuming an existing chat.
B Keep 0.166/0.167, but start the app-server with a launch override that matches the chat provider. Launch overrides count in the "latest config". Works with the current binary, but one app-server process gets one default provider. If JB and personal chats share a process, the other one still breaks. This is what the agent's analysis calls "align the startup provider".
C Revert master to rust-v0.165.0, as in the 262.1102 EAP candidate. Known to work, but loses everything newer.

Option B in practice:

# Launch override: becomes part of current_cli_overrides(), so load_latest_config() agrees with the thread
# (root-level -c, passed through to the app-server subcommand)
codex -c model_provider='"custom-gateway"' app-server

Workaround for affected users until a fixed build

Keep wire available for the terminal CLI, but stop it being the top-level default. Move it into a profile in the Codex config the wire tool edits (usually ~/.codex/config.toml):

# before
model_provider = "wire"

# after: no top-level default; use `codex -p wire` in the terminal
[profiles.wire]
model_provider = "wire"

Restart Air afterwards, and start a new chat: older chats keep the provider they were created with. I have not tested this workaround. It follows from the code above, because without a top-level default the "latest config" falls back to the same provider, or Air's launch overrides win.

One case the upgrade does not fix. If the central tool writes a managed requirement, such as model_provider in a requirements.toml or a cloud policy, rather than a normal config value, the remaining policy check in 0.168.0+ still rejects other providers. The error is then modelProviderPolicyConflict: "...your organization requires “wire”...". That is a different message from the one reported. If it appears after the bump, look there.

5. How to verify a fix

  1. Wire Codex with the central CLI tool, so the user config has model_provider = "wire".
  2. Start Air with the candidate Codex build. Open a new Codex chat with the JB subscription and send a prompt. Repeat with a personal subscription.
  3. Expected: the prompt reaches the gateway and gets an answer, with no "This chat uses …" error.
  4. Resume an older chat after restarting Air. Expected: it continues on its saved provider.
  5. Regression check: run the same steps with an unwired Codex config.
